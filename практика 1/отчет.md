### TL;DR — главное за 30 секунд

- Поднят полный стек **MinIO → Lakekeeper (Iceberg REST Catalog) → Trino**, сверху — **Metabase** как BI.
- Построен медальон **Bronze → Silver → Gold** для TPC-H Q10 (топ-20 клиентов по выручке от возвратов за Q4 1993); Gold-результат совпал с эталонным ответом TPC-H на `sf1`.
- Прогнан бенчмарк **8 комбинаций** формат × кодек (Parquet/ORC × NONE/SNAPPY/GZIP/ZSTD) на `lineitem` (6 млн строк) + отдельное контролируемое сравнение **GZIP vs ZSTD** на Bronze.
- Итог по кодекам: **ZSTD — лучший выбор по умолчанию** (сжимает почти как GZIP, пишет и читает быстрее); **GZIP** оправдан только для холодных архивов; **ORC** на плоской TPC-H-таблице крупнее Parquet при любом кодеке.
- Живьём показаны **schema evolution** (`ALTER TABLE ADD COLUMN`) и **time travel + rollback** (`FOR VERSION AS OF`, `rollback_to_snapshot`).
- По пути реально встретились и разобраны 3 проблемы: OOM у Trino на 8 ГБ RAM, несовместимость драйвера `presto-jdbc` в Metabase с актуальным Trino, различие fine-grained/classic GitHub-токенов при push.

Проверено через `docker compose ps` — все сервисы в статусе `healthy`.

|---|---|---|

Базовый стек (MinIO, Postgres, Lakekeeper, Trino) поднимается одной командой из `docker-compose.yml` в корне репозитория:


## 5. Тесты производительности: GZIP vs ZSTD на Bronze

Контролируемое сравнение (в отличие от приложения — здесь только 2 таблицы, каждая создана сразу после чистого перезапуска Trino, без эффекта «очереди запусков»). Две копии `bronze.raw_lineitem`, отличается только `compression_codec`. Запрос — тот же джойн/фильтр, что в Q10 (`raw_orders ⋈ raw_lineitem_<codec>`, `returnflag='R'`, Q4 1993, топ-20 по выручке).

| Сжатие | Время записи, с | Время запроса, с | Размер, МБ | Вывод |
|---|---|---|---|---|
| **GZIP** | 22.63 | 6.48 | 65.18 | Сжимает практически так же, как ZSTD (разница в размере <1%), но заметно медленнее и на запись, и на чтение |
| **ZSTD** | 20.09 | 4.14 | 65.68 | Быстрее GZIP на ~11% по записи и на ~36% по запросу, при практически том же размере на диске |

**Вывод:** на `lineitem` (в основном числовые/decimal-колонки) у GZIP нет преимущества, которое оправдало бы цену по CPU. Для данных, которые читаются чаще одного раза (а Bronze читается при каждом пересчёте Silver), **ZSTD — явно лучший выбор**. GZIP был бы оправдан только для данных, которые пишутся один раз и почти не читаются (холодный архив), где решает только место на диске.

> Время запроса — через `time docker exec lakehouse-trino-1 trino --execute "..."` (по смыслу то же, что `system.runtime.queries`, но проще для разовых замеров).

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

**Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)?**
Обычная БД (Postgres/MySQL) хранит и вычисляет на одной машине/кластере с привязкой данных к конкретному движку — масштабирование вширь дорогое, а формат хранения проприетарный (доступ только через саму БД). Lakehouse разделяет **хранение** (дешёвое объектное S3-хранилище, данные — открытые parquet/orc-файлы) и **вычисления** (любой движок — Trino, Spark, DuckDB — читает те же файлы через открытый каталог типа Iceberg). Это дешевле на больших объёмах (платишь за ГБ в S3, а не в проприетарной БД), гибче (не привязан к одному движку) и при этом даёт SQL и ACID-транзакции, которых не было у классического data lake (просто файлы в S3 без каталога и транзакций).

**Пример schema evolution на Silver.** На `silver.lakehouse.dim_customer` выполнено `ALTER TABLE ... ADD COLUMN loyalty_tier varchar`. Что произошло:

1. У всех существующих 150 000 строк новая колонка стала `NULL` (проверено `loyalty_tier IS NULL` → `true`); старые parquet-файлы **не переписывались** — Iceberg просто обновил схему в метаданных.
2. Важная деталь: `ALTER TABLE ADD COLUMN` **не создал новый снапшот** в `$snapshots` (до и после `ALTER` в таблице снапшотов значится один и тот же `snapshot_id`) — изменение схемы в Iceberg чисто метаданное, а не версия данных.
3. После `INSERT` новой строки с заполненным `loyalty_tier='GOLD'` появился новый снапшот (`operation: append`), и новая строка уже содержит значение в новой колонке.

Итог: старые и новые файлы с разными схемами мирно читаются вместе — это и есть schema evolution без даунтайма и без backfill.

**Пример восстановления данных из снапшота (time travel).** На `dim_customer` после `INSERT` тестовой строки (`custkey=999999`) снапшотов стало два:

```sql
-- в текущей версии строка есть
SELECT count(*) FROM silver.lakehouse.dim_customer WHERE custkey=999999;                                   -- 1

-- time travel на снапшот ДО вставки — строки там не было
SELECT count(*) FROM silver.lakehouse.dim_customer
  FOR VERSION AS OF 5376283007035176433 WHERE custkey=999999;                                              -- 0

-- восстановление: откат текущей таблицы к этому снапшоту
ALTER TABLE silver.lakehouse.dim_customer EXECUTE rollback_to_snapshot(snapshot_id => 5376283007035176433);

SELECT count(*) FROM silver.lakehouse.dim_customer WHERE custkey=999999;                                    -- 0 (после rollback)
SELECT count(*) FROM silver.lakehouse.dim_customer;                                                         -- 150000 (как до инцидента)
```

Это ровно то восстановление, которое нужно при ошибочной загрузке/INSERT: откатить таблицу к снапшоту до инцидента без восстановления из внешнего бэкапа.

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| **Metabase** (BI) | Из вариантов BI/движок/каталог выбран BI — слои «движок» и «каталог» уже закрыты Trino/Lakekeeper. Metabase — один контейнер, встроенная H2 под собственные метаданные, поднимается одним `docker run`, есть драйвер под Trino-протокол |

**Скрипт развёртывания:**

```bash
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase
```

Вторая команда подключает Metabase к той же docker-сети, что Trino/Lakekeeper/MinIO: без неё Metabase резолвит `host.docker.internal` на внутренний gateway Docker Desktop, с которого обратно на опубликованный порт 8080 попасть не удаётся. Рабочий путь — обращаться к Trino по DNS-имени сервиса `trino` внутри общей сети `lakehouse_lakehouse`.

**Подключение к lakehouse** (через REST API Metabase, без ручного клика по wizard — для воспроизводимости):

```bash
# 1. создать администратора (одноразово, через setup-token из /api/session/properties)
curl -X POST http://localhost:3000/api/setup -d '{"token": "...", "user": {...}}'

# 2. подключить каталог bronze Trino как источник данных
curl -X POST http://localhost:3000/api/database \
  -H "X-Metabase-Session: <session>" \
  -d '{
    "engine": "starburst",
    "name": "Lakehouse Bronze (Trino)",
    "details": {"host": "trino", "port": 8080, "catalog": "bronze", "schema": "lakehouse", "user": "trino", "ssl": false}
  }'
```

**Результат:** Metabase (`initial_sync_status: complete`) обнаружил все 4 таблицы Bronze-слоя (`raw_customer`, `raw_orders`, `raw_lineitem`, `raw_nation`) и успешно выполнил через `/api/dataset` тестовый SQL-запрос напрямую к `bronze.lakehouse.raw_customer` (`status: completed`, вернулись реальные строки) — цепочка Metabase → Trino → Lakekeeper → MinIO подтверждена работающей.

> **Нетривиальный момент.** Драйвер `presto-jdbc`, рекомендованный документацией Metabase для Trino, в этой связке стабильно возвращал `Authentication failed: ... X-Trino-User must be sent` независимо от переданного поля `user`. Переключение на драйвер `starburst` (тот же wire-протокол Trino, актуальнее поддерживает заголовки аутентификации) решило проблему без каких-либо изменений на стороне Trino.

## Приложение. Полный бенчмарк форматов/кодеков (гайд 3)

Parquet/ORC × 4 кодека на `tpch.sf1.lineitem` (6 001 215 строк), отдельная схема `bench.lakehouse` (свой warehouse и бакет MinIO). Каждая из 8 таблиц — `CREATE TABLE ... WITH (format=..., compression_codec=...) AS SELECT * FROM tpch.sf1.lineitem`. **Метаданные.** Манифест текущего снапшота у каждой таблицы — 1 файл, 8–9 КБ (например `parquet_zstd` — 8833 байт, `orc_none` — 8515 байт) против 142–453 **МБ** данных: метаданные составляют тысячные доли процента от объёма данных, накладные расходы Iceberg-каталога на этом объёме не имеют практического значения.

**Ответы на вопросы из гайда:**

1. **Размер.** Сильнее всего сжал `GZIP` в обоих форматах (ORC: `NONE→GZIP` −66.9%; Parquet −60.3%), `ZSTD` почти не отстал (ORC −64.4%, Parquet −58.5%). `ORC` при одинаковом кодеке стабильно *крупнее* `Parquet` (например `NONE`: 452.62 МБ против 356.65 МБ) — на плоской таблице без вложенных структур у ORC нет преимущества, которое обещано для сложных схем.
2. **Запись.** В этом прогоне `GZIP` оказался не медленнее, а даже немного *быстрее* `NONE` — противоречит теории («сжимать нечего» должно быть быстрее всего). См. блок «Ограничения методики» ниже — это не характеристика кодека, а артефакт порядка запуска.
3. **Чтение.** `NONE` не был самым быстрым на чтение ни в одном из двух форматов (ORC `NONE` — самый медленный из всех восьми: 5.55с cold), хотя распаковывать ему нечего — потому что с диска/MinIO читается кратно больше байт (452 МБ против 142–221 МБ у сжатых вариантов): на этом объёме чтение упирается в объём I/O, а не в CPU распаковки.
4. **Сводный компромисс.** Для горячих данных, которые читают много и часто параллельно, разумен `SNAPPY` — минимальная нагрузка на CPU при чтении. `ZSTD` — дефолт на все данные без явной причины отклоняться (подтверждено в п. 5 на Bronze). `GZIP` оправдан только там, где место на диске дороже CPU и данные читаются редко (архив, холодный слой) — в этом эксперименте он не дал ощутимого выигрыша в размере против `ZSTD`, зато стабильно медленнее на запись при честном (контролируемом) замере.
5. **Метаданные и кэш.** Манифесты (8–9 КБ) меньше данных (142–453 МБ) в десятки тысяч раз. Разница cold/warm на этом прогоне оказалась небольшой и не всегда однозначной — см. ниже.

### Ограничения методики бенчмарка (честно про шум в цифрах)

Чтобы не выдавать артефакты замера за выводы о кодеках, явно фиксирую, где цифры из приложения нужно читать с осторожностью:

- **Эффект «первого запуска».** В обоих батчах (Parquet и ORC) `ZSTD`-таблица создавалась первой сразу после `docker restart` и оказалась заметно быстрее остальных (52.9с и 52.8с против 70–130с у соседей) — вероятно, выигрыш даёт «чистая» JVM без конкуренции за ресурсы, а не сам кодек. Для изолированного замера нужно перезапускать Trino перед **каждой** таблицей; именно так сделано в п. 5 — там результат (`ZSTD` быстрее `GZIP`) уже совпал с теорией.
- **Ресурсные ограничения машины.** 8 ГБ RAM и лимит Trino ~3.8 ГБ — на этом фоне Trino один раз реально упал по OOM (см. п. 1); фоновая нагрузка от одновременно работающих контейнеров (Lakekeeper, MinIO, Postgres, Metabase) добавляет шум в замеры времени.
- **cold/warm на малом объёме.** На `sf1` файлы (142–453 МБ) полностью помещаются в page cache ОС уже после одного прохода — поэтому разница cold/warm местами тонет в фоновом шуме загруженной машины. Это не опровергает идею «тёплый прогон быстрее», а показывает предел применимости на небольших объёмах: для чистого замера нужен `sf10`+ и изолированная машина.

## 7. Выводы

**Медальон — это конкретные решения, не три копии данных.** Bronze хранит источник как есть и ничего не выбрасывает; Silver — единственное место, где живут бизнес-фильтры и денормализация (join с `nation` в `dim_customer`, фильтр по кварталу и `returnflag` в `fct_returned_lineitem`); Gold — чистый `GROUP BY` без единого джойна, потому что вся сложность уже решена ниже по пайплайну. Из-за этого Gold-таблица крошечная (3 КБ на 20 строк), а основной вес (69 МБ из ~112 МБ всего медальона) несёт Bronze `raw_lineitem` — это ожидаемо и правильно: детализация должна жить внизу, агрегат наверху.

**Кодеки: ZSTD — обоснованный дефолт.** На TPC-H `lineitem` (в основном числовые/decimal колонки) разница в сжатии между ZSTD и GZIP минимальна (<1% в контролируемом тесте п. 5), а по скорости записи и чтения ZSTD уверенно выигрывает. Выбор дефолтного кодека Iceberg-коннектора Trino (ZSTD) для такого типа данных оправдан; сознательно включать GZIP стоит только для по-настоящему холодных, редко читаемых архивов.

**Метаданные Iceberg не являются проблемой на этих объёмах.** Манифесты по 8–9 КБ на фоне десятков–сотен МБ данных — накладные расходы каталога пренебрежимо малы; полный 8-вариантный бенчмарк подтвердил общую картину из гайда и по разнице размеров между `NONE` и сжатыми вариантами (у ORC `NONE→GZIP` почти ×3).

**Инфраструктурный урок не из таблицы.** Trino реально упал по OOM при нагрузке, близкой к `sf10`, на машине с ограниченной памятью — живое напоминание, что выбор `sfN` для лабораторной должен подстраиваться под доступные ресурсы, а не только под учебный ориентир из гайда. Аналогично несовпадение драйвера `presto-jdbc` с актуальным Trino (решено переходом на `starburst`) показывает, что «рекомендованная» в документации BI-интеграция не гарантирует совместимости с конкретной версией движка — это стоит проверять эмпирически, а не доверять документации вслепую.
