## 2. Поднятые сервисы — и почему именно они

Проверено через `docker compose ps` — все сервисы в статусе `healthy`.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO (образ `pgsty/silo`, форк) | S3-совместимое объектное хранилище — сюда физически падают parquet/orc-файлы всех слоёв (bronze/silver/gold/bench) | Открытый исходный код, полная совместимость с S3 API — то же самое поведение, что и в облаке (AWS S3/GCS), но без затрат и без аккаунта. Официальные `minio/minio`/`quay.io/minio/minio` сняты с публичных реестров в 2026 — `pgsty/silo` — поддерживаемый drop-in форк с тем же API, портами и переменными окружения, поэтому замена не потребовала менять ни одной команды, кроме имени образа |
| PostgreSQL 17 | БД, где Lakekeeper хранит метаданные каталога (какие warehouse/таблицы/снапшоты существуют) | Де-факто стандартный backend для Iceberg REST-каталогов (используется в документации самого Lakekeeper); надёжный, с понятным `pg_isready`-health-check для docker-compose |
| Lakekeeper | Iceberg REST Catalog — хранит метаданные таблиц (файлы, снапшоты, схемы) отдельно от самих данных | Открытая реализация спецификации Iceberg REST Catalog — к такому каталогу может подключиться любой REST-совместимый движок (Trino, Spark, DuckDB) без проприетарной интеграции (в отличие от AWS Glue). Поддерживает множество независимых `warehouse` — этим воспользовались для физического разделения слоёв медальона (4 warehouse: `bronze`, `silver`, `gold`, `bench`, плюс `demo` из гайда 1) |
| Trino | SQL-движок: ходит в Lakekeeper за метаданными и читает/пишет parquet/orc в MinIO | Один SQL-диалект поверх всех каталогов и слоёв сразу (трёхчастные имена `catalog.schema.table`), встроенный коннектор `tpch` для генерации тестовых данных без закачки файлов, системные таблицы Iceberg (`$files`, `$snapshots`, `$manifests`, `$properties`) для измерений без похода в консоль MinIO |
| Metabase | BI-слой поверх Bronze (п. 6.2) | Однo-контейнерный open-source BI, не требует отдельной БД для своих метаданных (встроенный H2), поднимается одной командой `docker run`; умеет подключаться к Trino по JDBC |

### Скрипты, которыми поднимал стек

Базовый стек (MinIO, Postgres, Lakekeeper, Trino) поднят через `docker-compose.yml` (лежит в корне репозитория) одной командой:

```bash
docker compose up -d
```

Слои медальона и бенчмарк docker-compose изначально не создавал — я дополнил `docker-compose.yml` сервисами `lakekeeper-warehouse-medallion` (регистрирует 4 дополнительных warehouse: `bronze`/`silver`/`gold`/`bench` через REST API Lakekeeper по тому же паттерну, что и штатный `lakekeeper-warehouse`) и `metabase`, а также расширил `minio-init`, чтобы он создавал бакеты `bronze`/`silver`/`gold`/`bench` вместе со штатным `warehouse`. Теперь весь стек, включая медальон и BI, поднимается той же одной командой `docker compose up -d`.

Catalog-файлы Trino (`catalog/bronze.properties`, `catalog/silver.properties`, `catalog/gold.properties`, `catalog/bench.properties`, `catalog/tpch.properties`) — по образцу `catalog/lakekeeper.properties` из гайда 1, меняется только `iceberg.rest-catalog.warehouse`.

Фактически выполненные команды (после того как `docker compose up -d` поднял базу):

```bash
# бакеты bronze/silver/gold/bench в MinIO
docker run --rm --entrypoint /bin/sh --add-host host.docker.internal:host-gateway \
  pgsty/mc:latest -c "mc alias set m http://host.docker.internal:9000 minioadmin minioadmin && \
  mc mb --ignore-existing m/bronze && mc mb --ignore-existing m/silver && \
  mc mb --ignore-existing m/gold && mc mb --ignore-existing m/bench"

# регистрация warehouse bronze/silver/gold/bench в Lakekeeper (цикл по 4 json-файлам, см. create-warehouse-*.json)
for wh in bronze silver gold bench; do
  curl -X POST http://localhost:8181/management/v1/warehouse \
    -H "Content-Type: application/json" -d @create-warehouse-$wh.json
done

docker restart lakehouse-trino-1   # перечитать новые catalog/*.properties

# BI-инструмент
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase   # чтобы Metabase видел Trino по DNS-имени "trino"
```

## 3. Разбор запроса — какие данные нужны

Вариант 2 — Q10 «Returned Item Reporting»: топ-20 клиентов по выручке от **возвращённых** позиций (`returnflag = 'R'`) за 4-й квартал 1993 года.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `customer` | `custkey`, `name`, `acctbal`, `address`, `phone`, `comment`, `nationkey` | джойн с `orders` по `custkey`; джойн с `nation` по `nationkey`; `name/acctbal/address/phone/comment` — в итоговый вывод без изменений |
| `orders` | `orderkey`, `custkey`, `orderdate` | фильтр `orderdate >= 1993-10-01 AND orderdate < 1994-01-01` (4-й квартал 1993); джойн с `customer` по `custkey` и с `lineitem` по `orderkey` |
| `lineitem` | `orderkey`, `extendedprice`, `discount`, `returnflag` | фильтр `returnflag = 'R'`; агрегат `sum(extendedprice * (1 - discount))` как `revenue` |
| `nation` | `nationkey`, `name` | джойн с `customer` по `nationkey`; `name` → колонка `nation` в выводе |

## 5. Тесты производительности

Сравнение `GZIP` vs `ZSTD` на отдельных копиях `bronze.raw_lineitem` (та же таблица, что в п. 4, пересоздана дважды с явным `compression_codec`). Запрос — top-20 клиентов по выручке за возвраты (Q10-джойн `raw_orders ⋈ raw_lineitem_<codec>`, фильтр `returnflag='R'` + 4-й квартал 1993).

| Сжатие на Bronze | Время записи, с | Время запроса, с | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|---|
| GZIP | 22.63 | 6.48 | 65.18 | Сжимает практически так же, как ZSTD (разница в размере <1%), но заметно медленнее и на запись, и на чтение — на `lineitem` (в основном числовые/decimal-колонки, строк мало) у GZIP нет преимущества, которое оправдало бы цену по CPU |
| ZSTD | 20.09 | 4.14 | 65.68 | Быстрее GZIP на ~11% по записи и на ~36% по этому запросу, при практически том же размере на диске. Для данных, которые читаются чаще одного раза (а Bronze читается на построение Silver регулярно), ZSTD — явно лучший выбор. GZIP был бы оправдан только для данных, которые пишутся один раз и почти не читаются (холодный архив), где решает только место на диске |

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная БД (Postgres/MySQL) хранит и вычисляет на одной машине/кластере с привязкой данных к конкретному движку — масштабирование вширь дорогое, а формат хранения проприетарный (доступ только через саму БД). Lakehouse разделяет **хранение** (дешёвое объектное S3-хранилище, данные как открытые parquet/orc-файлы) и **вычисления** (любой движок — Trino, Spark, DuckDB — может читать те же файлы через открытый каталог типа Iceberg). Это и дешевле на больших объёмах (платишь за ГБ в S3, а не за ГБ в проприетарной БД), и гибче (не привязан к одному движку), и при этом даёт SQL и ACID-транзакции, которых не было у классических data lake (просто файлы в S3 без каталога/транзакций) |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | На `silver.lakehouse.dim_customer` выполнено `ALTER TABLE ... ADD COLUMN loyalty_tier varchar`. Результат: (1) у всех существующих 150 000 строк новая колонка стала `NULL` (проверено `loyalty_tier IS NULL` → `true`), старые parquet-файлы **не переписывались** — Iceberg просто обновил схему в метаданных; (2) что важно — `ALTER TABLE ADD COLUMN` **не создал новый снапшот** в `$snapshots` (проверено: до и после `ALTER` в таблице снапшотов значится один и тот же snapshot_id) — изменение схемы в Iceberg чисто метаданное, а не версия данных; (3) после `INSERT` новой строки с заполненным `loyalty_tier='GOLD'` появился новый снапшот (`operation: append`), и новая строка уже содержит значение в новой колонке. Итог: старые и новые файлы с разными схемами мирно читаются вместе — это и есть schema evolution без даунтайма и без backfill |
| Пример скрипта восстановления данных из снапшота (time travel) | На `dim_customer` после `INSERT` тестовой строки (`custkey=999999`) снапшотов стало два. Восстановление: `SELECT count(*) FROM silver.lakehouse.dim_customer FOR VERSION AS OF 5376283007035176433 WHERE custkey=999999` → `0` (строки не было в старом снапшоте, хотя в текущей версии таблицы она есть — `count=1`). Затем выполнен реальный откат: `ALTER TABLE silver.lakehouse.dim_customer EXECUTE rollback_to_snapshot(snapshot_id => 5376283007035176433)` — после этого `SELECT count(*) FROM dim_customer` снова `150000`, тестовая строка исчезла из текущей версии таблицы. Это ровно то восстановление, которое нужно при ошибочной загрузке/INSERT: откатить таблицу к снапшоту до инцидента без восстановления из внешнего бэкапа |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Metabase (BI) | Из вариантов BI/движок/каталог выбран BI, т.к. остальные слои уже закрыты движком Trino. Metabase — однo-контейнерный open-source BI без внешней БД для своих метаданных (встроенная H2), поднимается одним `docker run` и имеет готовый драйвер под Trino-протокол (через движок `starburst`, полностью совместимый по wire-протоколу с open-source Trino) |

**Скрипт развёртывания:**

```bash
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase
```
(второй командой Metabase подключён к той же docker-сети, что и Trino/Lakekeeper/MinIO, — иначе он резолвит `host.docker.internal` на внутренний gateway Docker Desktop, с которого обратно на опубликованный порт `8080` попасть не удаётся; рабочий путь — обращаться к Trino по DNS-имени сервиса `trino` внутри общей docker-сети `lakehouse_lakehouse`).

**Подключение к lakehouse (через REST API Metabase, без ручного клика по wizard — для воспроизводимости):**

```bash
# 1. создать администратора (одноразово, через setup-token из /api/session/properties)
curl -X POST http://localhost:3000/api/setup -d '{"token": "...", "user": {...}}'

# 2. подключить каталог bronze Trino как источник данных
curl -X POST http://localhost:3000/api/database \
  -H "X-Metabase-Session: <session>" \
  -d '{
    "engine": "starburst",
    "name": "Lakehouse Bronze (Trino)",
    "details": {"host": "trino", "port": 8080, "catalog": "bronze", "schema": "lakehouse", "user": "trino", "ssl": false}
  }'
```

**Результат:** Metabase (`initial_sync_status: complete`) обнаружил все 4 таблицы Bronze-слоя (`raw_customer`, `raw_orders`, `raw_lineitem`, `raw_nation`) и успешно выполнил через свой `/api/dataset` тестовый SQL-запрос напрямую к `bronze.lakehouse.raw_customer` (`status: completed`, вернулись реальные строки) — то есть цепочка Metabase → Trino → Lakekeeper → MinIO подтверждена работающей.

> Попутно найден нетривиальный момент: драйвер `presto-jdbc`, который в документации Metabase рекомендован для Trino, в этой связке стабильно возвращал `Authentication failed: ... X-Trino-User must be sent` независимо от переданного поля `user` — переключение на драйвер `starburst` (тот же wire-протокол Trino, актуальнее поддерживает заголовки аутентификации) решило проблему без каких-либо изменений на стороне Trino.

## Приложение. Полный бенчмарк форматов/кодеков (гайд 3): Parquet/ORC × 4 кодека на `tpch.sf1.lineitem`

Отдельная схема `bench.lakehouse` (своя warehouse `bench`, свой бакет MinIO), 8 таблиц `lineitem_<формат>_<кодек>`, каждая — `CREATE TABLE ... WITH (format=..., compression_codec=...) AS SELECT * FROM tpch.sf1.lineitem` (6 001 215 строк). Размер и число файлов — через `$files`, время записи — через `time docker exec ... trino --execute`, агрегация — классический TPC-H Q1 (`GROUP BY returnflag, linestatus`), каждый прогон cold (сразу после `docker restart lakehouse-minio-1 lakehouse-trino-1`) и warm (повторный прогон той же сессии).

| Вариант | Размер, МБ | Файлов | Время записи, с | Агрегация cold, с | Агрегация warm, с |
|---|---|---|---|---|---|
| parquet_none | 356.65 | 4 | 80.31 | 3.80 | 3.17 |
| parquet_snappy | 199.36 | 4 | 70.82 | 3.38 | 3.46 |
| parquet_gzip | 141.71 | 4 | 72.51 | 2.73 | 2.61 |
| parquet_zstd | 148.16 | 4 | 52.94 | 4.54 | 2.91 |
| orc_none | 452.62 | 4 | 127.68 | 5.55 | 5.45 |
| orc_snappy | 221.43 | 4 | 120.61 | 3.20 | 3.35 |
| orc_gzip | 149.65 | 4 | 117.44 | 2.80 | 3.05 |
| orc_zstd | 161.19 | 4 | 52.82 | 3.92 | 3.13 |

Метаданные: манифест текущего снапшота у каждой из этих таблиц — 1 файл, 8–9 КБ (например `parquet_zstd` — 8833 байт, `orc_none` — 8515 байт) против 142–453 **МБ** данных — то есть метаданные составляют тысячные доли процента от объёма данных, накладные расходы Iceberg-каталога на этом объёме не имеют практического значения.

**Ответы на вопросы из гайда:**

1. **Размер.** Сильнее всего сжал `GZIP` в обоих форматах (ORC: `NONE→GZIP` на 66.9% меньше; Parquet: на 60.3% меньше), `ZSTD` почти не отстал (ORC −64.4%, Parquet −58.5%). `ORC` при одинаковом кодеке стабильно *крупнее* `Parquet` (например `NONE`: 452.62 МБ против 356.65 МБ) — на плоской таблице без вложенных структур у ORC нет преимущества, которое обещано для сложных схем.
2. **Запись.** В этом прогоне `GZIP` оказался не медленнее, а даже немного *быстрее* `NONE` (ORC: 117.44с против 127.68с) — это противоречит теории («сжимать нечего» должно быть быстрее всего) и честно объясняется артефактом замера: `ZSTD`-таблица в каждом из двух батчей (Parquet и ORC) создавалась первой после перезапуска Trino и оказалась самой быстрой в обоих случаях (52.9с и 52.8с) — то есть на первую запись в «чистой» JVM/без конкуренции за ресурсы влияет не кодек, а порядок выполнения и состояние контейнера (на машине с 8 ГБ RAM и лимитом Trino ~3.8 ГБ это заметно). Для изолированного замера стоило бы перезапускать Trino перед **каждой** таблицей и усреднять несколько повторов — в п. 5 (сравнение GZIP/ZSTD на Bronze) это сделано именно так, и там результат уже совпал с теорией (`ZSTD` быстрее `GZIP`).
3. **Чтение.** `NONE` не был самым быстрым на чтение ни в одном из двух форматов (ORC `NONE` — самый медленный из всех восьми: 5.55с cold), хотя распаковывать ему нечего — потому что с диска/MinIO читается кратно больше байт (452 МБ против 142–221 МБ у сжатых вариантов), и на этом объёме чтение упирается не в CPU распаковки, а в объём I/O.
4. **Сводный компромисс.** Для горячих данных, которые читают много и часто параллельно (а не только пишут), я бы взял `SNAPPY` — минимальная нагрузка на CPU при чтении, сжатие слабее, но предсказуемо быстрое. `ZSTD` — дефолт на все данные, где нет явной причины отклоняться (что и подтвердилось в п. 5 на Bronze). `GZIP` оправдан только там, где место на диске дороже CPU и данные читаются редко (архив, холодный слой) — на нашем эксперименте он не дал ощутимого выигрыша в размере против `ZSTD`, зато стабильно медленнее на запись при честном (одиночном, без эффекта «первой после рестарта» таблицы) замере.
5. **Метаданные и кэш.** Манифесты (8–9 КБ) меньше данных (142–453 МБ) в десятки тысяч раз — метаданные Iceberg ничтожны даже на этом небольшом `sf1`-объёме, тем более они не станут проблемой на больших таблицах. Разница cold/warm на этом прогоне оказалась небольшой и не всегда однозначной (у части таблиц warm был даже на сотые доли секунды медленнее cold) — вероятная причина: на `sf1` файлы (142–453 МБ) полностью помещаются в page cache ОС уже после одного прохода, а 8ГБ-машина с несколькими одновременно работающими контейнерами (Trino, Lakekeeper, MinIO, Postgres, Metabase) создавала фоновый шум, сопоставимый по величине с самим эффектом кэша. Это не опровергает идею «тёплый прогон быстрее», а показывает её предел применимости: на небольших объёмах и загруженной машине разница тонет в шуме — для чистого замера нужен был бы `sf10`+ и изолированная машина.

## 7. Выводы

Медальонная архитектура (Bronze → Silver → Gold) на практике — это не просто «три копии данных», а конкретные решения: Bronze хранит источник как есть и ничего не выбрасывает, Silver — это единственное место, где живут бизнес-фильтры и денормализация (join с `nation` в `dim_customer`, фильтр по кварталу и `returnflag` в `fct_returned_lineitem`), а Gold — чистый `GROUP BY` без единого джойна, потому что вся сложность уже решена ниже по пайплайну. Из-за этого Gold-таблица получилась крошечной (3 КБ на 20 строк), а основной вес (69 МБ из ~110 МБ всего медальона) несёт Bronze `raw_lineitem` — это ожидаемо и правильно: детализация должна жить внизу, агрегат наверху. Эксперимент с кодеками показал, что на TPC-H `lineitem` (в основном числовые/decimal колонки) разница в сжатии между ZSTD и GZIP минимальна (<1%), а по скорости записи/чтения ZSTD уверенно выигрывает — поэтому выбор дефолтного кодека Iceberg-коннектора Trino (ZSTD) для этого типа данных оправдан, и сознательно включать GZIP стоит только для по-настоящему холодных, редко читаемых архивов. Полный 8-вариантный бенчмарк (Parquet/ORC × 4 кодека, `sf1`) подтвердил общую картину из гайда: разница в размере между `NONE` и сжатыми вариантами — кратная (у ORC `NONE`→`GZIP` почти ×3), а метаданные Iceberg (манифесты по 8–9 КБ) пренебрежимо малы на фоне десятков–сотен МБ данных — накладные расходы каталога не являются проблемой на таких объёмах. Отдельно полезным оказался урок не из таблицы: Trino реально упал по OOM при параллельной нагрузке на машине с ограниченной памятью — живое напоминание, что выбор `sfN` для лабораторной должен подстраиваться под доступные ресурсы, а не только под учебный ориентир из гайда.
