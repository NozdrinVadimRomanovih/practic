## 2. Поднятые сервисы — и почему именно они

Проверено через `docker compose ps` — всё в статусе `healthy`.

| Сервис | Роль | Почему он |
|---|---|---|
| MinIO (`pgsty/silo`) | Хранит сами файлы (parquet/orc) | Open-source, ведёт себя как S3, но бесплатно. Оригинальный `minio/minio` в 2026 убрали из публичных реестров, `pgsty/silo` — рабочий форк с тем же API |
| PostgreSQL 17 | БД для метаданных Lakekeeper | Стандартный выбор по документации Lakekeeper, простой health-check |
| Lakekeeper | Iceberg-каталог: кто какие таблицы/снапшоты создал | Открытая реализация REST-каталога, подключается любой движок (Trino/Spark/DuckDB). Поддерживает несколько warehouse — на этом держится разделение слоёв медальона |
| Trino | SQL-движок, читает/пишет данные через Lakekeeper в MinIO | Один SQL над всеми слоями сразу, встроенный генератор тестовых данных `tpch`, системные таблицы `$files`/`$snapshots` для всех замеров |
| Metabase | BI поверх Bronze (п. 6.2) | Один контейнер, своя встроенная БД, поднимается одной командой |

### Как поднимал стек

Базовый стек — одной командой из `docker-compose.yml`:

```bash
docker compose up -d
```

В исходном файле не было медальона и BI, я их добавил: сервис, который регистрирует 4 warehouse (`bronze`/`silver`/`gold`/`bench`), сервис `metabase`, и `minio-init` расширил, чтобы он создавал нужные бакеты. Catalog-файлы Trino (`catalog/bronze.properties` и т.д.) — копия штатного файла, поменяна только строка с именем warehouse.

Команды, которые реально выполнял:

```bash
# бакеты в MinIO
docker run --rm --entrypoint /bin/sh --add-host host.docker.internal:host-gateway \
  pgsty/mc:latest -c "mc alias set m http://host.docker.internal:9000 minioadmin minioadmin && \
  mc mb --ignore-existing m/bronze && mc mb --ignore-existing m/silver && \
  mc mb --ignore-existing m/gold && mc mb --ignore-existing m/bench"

# warehouse в Lakekeeper
for wh in bronze silver gold bench; do
  curl -X POST http://localhost:8181/management/v1/warehouse \
    -H "Content-Type: application/json" -d @create-warehouse-$wh.json
done

docker restart lakehouse-trino-1   # чтобы подхватил новые catalog/*.properties

# BI
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase
```

## 5. Тесты производительности

### GZIP vs ZSTD на Bronze

Две копии `raw_lineitem`, отличаются только кодеком, обе созданы сразу после рестарта Trino. Запрос — тот же джойн из Q10.

| Сжатие | Время запроса, с | Размер, МБ | Вывод |
|---|---|---|---|
| GZIP | 6.48 | 65.18 | Сжимает почти как ZSTD (разница <1%), но пишет (22.63 с) и читает заметно медленнее |
| ZSTD | 4.14 | 65.68 | На запись быстрее на ~11%, на запрос — на ~36%, при том же размере |

Вывод: на `lineitem` GZIP не окупается. ZSTD даёт то же сжатие быстрее — он и лучше, кроме случая, когда данные пишутся раз и почти не читаются.

### Доп. бенчмарк: Parquet/ORC × 4 кодека

Дополнительно прогнал все 8 комбинаций формат×кодек на полной `lineitem` (6 млн строк), отдельная схема `bench`.

| Вариант | Размер, МБ | Время записи, с | Агрегация cold, с | Агрегация warm, с |
|---|---|---|---|---|
| parquet_none | 356.65 | 80.31 | 3.80 | 3.17 |
| parquet_snappy | 199.36 | 70.82 | 3.38 | 3.46 |
| parquet_gzip | 141.71 | 72.51 | 2.73 | 2.61 |
| parquet_zstd | 148.16 | 52.94 | 4.54 | 2.91 |
| orc_none | 452.62 | 127.68 | 5.55 | 5.45 |
| orc_snappy | 221.43 | 120.61 | 3.20 | 3.35 |
| orc_gzip | 149.65 | 117.44 | 2.80 | 3.05 |
| orc_zstd | 161.19 | 52.82 | 3.92 | 3.13 |

Метаданные (манифест) — 8–9 КБ на таблицу против сотен МБ данных: несущественно.

**Что видно:**

1. Сильнее всех сжал GZIP (ORC −67%, Parquet −60%), ZSTD почти не отстал. ORC при любом кодеке крупнее Parquet — на плоской таблице у него нет преимущества.
2. По времени записи здесь GZIP вышел даже быстрее NONE — это не про кодек, а артефакт замера (см. ниже).
3. NONE не самый быстрый на чтение (`orc_none` — самый медленный, 5.55 с), потому что читает больше байт с диска.
4. Для горячих данных — SNAPPY, по умолчанию — ZSTD, GZIP только для холодных архивов.
5. Разница cold/warm небольшая — объём мелкий, всё и так в кэше.

**Почему цифрам по записи не стоит доверять буквально.** В обоих батчах таблица с ZSTD писалась первой сразу после рестарта Trino и оказалась быстрее всех (52–53 с против 70–130 с у остальных) — скорее всего, дело в чистой JVM без конкуренции за ресурсы, а не в кодеке. Честный замер (с рестартом перед каждой таблицей) я сделал отдельно в сравнении GZIP/ZSTD выше — там результат совпал с теорией. Плюс машина слабая (8 ГБ RAM, Trino падал по OOM — см. раздел 1), и несколько контейнеров работают одновременно, это добавляет шум в цифры.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

**Зачем lakehouse, а не обычная БД.** Обычная БД считает и хранит на одном движке — масштабировать дорого, а данные доступны только через неё саму. Lakehouse разделяет хранение (дешёвый S3, открытые файлы parquet/orc) и вычисления (любой движок читает их через открытый каталог вроде Iceberg). Дешевле на больших объёмах, не привязан к одному движку, и при этом есть SQL и транзакции — которых не было у обычного data lake (просто файлы без каталога).

**Schema evolution на Silver.** Сделал `ALTER TABLE dim_customer ADD COLUMN loyalty_tier varchar`. У старых 150 000 строк колонка стала `NULL`, старые файлы не переписались — Iceberg просто обновил схему в метаданных. Интересно: сам `ALTER` не создал новый снапшот — это чисто метаданные, не версия данных. После `INSERT` новой строки с заполненным `loyalty_tier` появился новый снапшот (`append`). Старые и новые файлы с разными схемами читаются вместе, без простоя.

**Time travel / восстановление.** Вставил тестовую строку (`custkey=999999`) — снапшотов стало два. `SELECT count(*) ... FOR VERSION AS OF <старый_snapshot_id> WHERE custkey=999999` — вернул 0, хотя в текущей версии строка есть (`count=1`). Дальше сделал `ALTER TABLE ... EXECUTE rollback_to_snapshot(snapshot_id => ...)` — таблица вернулась к 150 000 строкам, тестовая строка пропала. Это и есть восстановление после ошибочной вставки без похода во внешний бэкап.

### 6.2. Подключить инструмент к lakehouse

Выбрал Metabase (BI) — движок и каталог уже заняты Trino/Lakekeeper. Один контейнер, своя БД, легко поднять.

```bash
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase
```

Вторая команда нужна, чтобы Metabase видел Trino по имени `trino` — без неё `host.docker.internal` ведёт не туда и порт 8080 недостижим.

Подключение сделал через REST API Metabase, не руками в UI:

```bash
curl -X POST http://localhost:3000/api/setup -d '{"token": "...", "user": {...}}'

curl -X POST http://localhost:3000/api/database \
  -H "X-Metabase-Session: <session>" \
  -d '{"engine": "starburst", "name": "Lakehouse Bronze (Trino)",
       "details": {"host": "trino", "port": 8080, "catalog": "bronze",
                    "schema": "lakehouse", "user": "trino", "ssl": false}}'
```

Metabase увидел все 4 таблицы Bronze и выполнил тестовый запрос — цепочка Metabase → Trino → Lakekeeper → MinIO работает.

Был неприятный момент: драйвер `presto-jdbc`, который советует документация Metabase для Trino, упорно отвечал ошибкой авторизации («X-Trino-User must be sent»), независимо от настроек. Помог драйвер `starburst` — тот же протокол, но без этой проблемы.

## 7. Выводы

Медальон на практике — это не три копии одних данных, а разделение труда. Bronze хранит всё как пришло. Silver — единственное место с бизнес-фильтрами и обогащением (джойн с nation, фильтр по кварталу и возврату). Gold делает только группировку, потому что вся сложность уже решена ниже. Отсюда и вес: Gold — 3 КБ, а основную массу (69 из ~112 МБ) тащит `raw_lineitem` в Bronze. Это нормально — детали внизу, агрегат наверху.

По кодекам: на `lineitem` ZSTD и GZIP сжимают почти одинаково, но ZSTD заметно быстрее пишет и читает. Дефолт Trino (ZSTD) выбран правильно для такого рода данных, GZIP имеет смысл только для холодных архивов.

Метаданные Iceberg (манифесты по 8–9 КБ) ничего не весят на фоне сотен МБ данных. И два практических урока, которых в таблицах не видно: во-первых, память реально ограничивает — Trino падал по OOM, и масштаб `sfN` нужно подбирать под железо, а не только по рекомендации гайда; во-вторых, «рекомендованный» в документации драйвер BI-инструмента не гарантирует совместимость с конкретной версией движка — это стоит проверять самому.
