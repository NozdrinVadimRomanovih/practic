На нём весь бенчмарк (8 таблиц, 16 замеров) считается за несколько минут и не вызывает сбоя контейнера, при этом разница между кодеками всё равно хорошо видна. |

## 2. Поднятые сервисы — и почему именно они

Состояние сервисов проверено командой `docker compose ps`, все сервисы в статусе `healthy`.

| Сервис | Роль | Почему выбран |
|---|---|---|
| MinIO (образ `pgsty/silo`) | Хранит файлы данных (parquet/orc) | Открытый код, поведение как у S3, без затрат на облако. Оригинальный образ `minio/minio` в 2026 году убрали из публичных реестров, `pgsty/silo` — рабочий форк с тем же API |
| PostgreSQL 17 | База данных для метаданных Lakekeeper | Простой и надёжный вариант с понятным health-check (`pg_isready`) |
| Lakekeeper | Iceberg-каталог: хранит сведения о таблицах и снапшотах | Открытая реализация REST-каталога Iceberg. К такому каталогу подключается любой движок — Trino, Spark, DuckDB. Поддерживает несколько независимых warehouse, на этом строится разделение слоёв медальона |
| Trino | SQL-движок: читает и пишет данные через Lakekeeper в MinIO | Единый SQL-язык для всех слоёв сразу, встроенный генератор тестовых данных `tpch`, системные таблицы `$files` и `$snapshots` для всех замеров в отчёте |
| Metabase | BI-инструмент поверх Bronze-слоя (раздел 6.2) | Один контейнер, собственная встроенная база метаданных, поднимается одной командой |

### Развёртывание стека

Весь стек описан в одном файле `docker-compose.yml`: MinIO, PostgreSQL, Lakekeeper, регистрация четырёх warehouse для слоёв медальона (`bronze`, `silver`, `gold`, `bench`), Trino и Metabase. Поднимается одной командой:

```bash
docker compose up -d
```

Trino узнаёт о каталогах через файлы-свойства в папке `catalog/`: для каждого слоя создан отдельный файл (`catalog/bronze.properties`, `catalog/silver.properties`, `catalog/gold.properties`, `catalog/bench.properties`, плюс `catalog/tpch.properties` для встроенного генератора данных). Файлы одинаковые, в каждом меняется только строка с именем warehouse.

Часть шагов нельзя описать внутри docker-compose — создание бакетов в MinIO и регистрация warehouse идут через REST-запросы к уже запущенным сервисам, поэтому они выполнены отдельными командами после старта базовых контейнеров:

```bash
# бакеты в MinIO
docker run --rm --entrypoint /bin/sh --add-host host.docker.internal:host-gateway \
  pgsty/mc:latest -c "mc alias set m http://host.docker.internal:9000 minioadmin minioadmin && \
  mc mb --ignore-existing m/bronze && mc mb --ignore-existing m/silver && \
  mc mb --ignore-existing m/gold && mc mb --ignore-existing m/bench"

# warehouse в Lakekeeper
for wh in bronze silver gold bench; do
  curl -X POST http://localhost:8181/management/v1/warehouse \
    -H "Content-Type: application/json" -d @create-warehouse-$wh.json
done

docker restart lakehouse-trino-1   # чтобы Trino подхватил catalog/*.properties

# BI-инструмент
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase
```

## 5. Тесты производительности

### GZIP и ZSTD на Bronze

Созданы две копии таблицы `raw_lineitem`, отличающиеся только кодеком, обе сразу после перезапуска Trino. Запрос для замера — тот же джойн, что в Q10.

| Сжатие | Время запроса, с | Размер, МБ | Вывод |
|---|---|---|---|
| GZIP | 6.48 | 65.18 | Сжимает почти так же, как ZSTD, разница в размере меньше 1%. Но заметно медленнее пишет (22.63 с) и читает |
| ZSTD | 4.14 | 65.68 | Быстрее на запись (разница около 11%) и на запрос (разница около 36%), при том же размере |

На данных типа `lineitem` GZIP не даёт выигрыша, который оправдал бы дополнительную нагрузку на процессор. ZSTD даёт такое же сжатие быстрее, поэтому он предпочтителен, кроме случаев, когда данные пишутся один раз и почти не читаются.

### Дополнительный бенчмарк: Parquet/ORC × 4 кодека

Дополнительно проведён бенчмарк всех 8 комбинаций формата и кодека на полной таблице `lineitem` (6 млн строк) в отдельной схеме `bench`.

| Вариант | Размер, МБ | Время записи, с | Агрегация cold, с | Агрегация warm, с |
|---|---|---|---|---|
| parquet_none | 356.65 | 80.31 | 3.80 | 3.17 |
| parquet_snappy | 199.36 | 70.82 | 3.38 | 3.46 |
| parquet_gzip | 141.71 | 72.51 | 2.73 | 2.61 |
| parquet_zstd | 148.16 | 52.94 | 4.54 | 2.91 |
| orc_none | 452.62 | 127.68 | 5.55 | 5.45 |
| orc_snappy | 221.43 | 120.61 | 3.20 | 3.35 |
| orc_gzip | 149.65 | 117.44 | 2.80 | 3.05 |
| orc_zstd | 161.19 | 52.82 | 3.92 | 3.13 |

Метаданные (манифест) занимают 8–9 КБ на таблицу против сотен МБ данных, это несущественная величина.

Сильнее всех сжал GZIP (ORC минус 67%, Parquet минус 60%), ZSTD отстал незначительно. ORC при любом кодеке крупнее Parquet: на плоской таблице у этого формата нет преимущества, которое обычно даёт работа со сложными схемами. По времени записи GZIP здесь оказался даже быстрее NONE, хотя так не должно быть, и причина не в кодеке — пояснение ниже. Вариант NONE не был самым быстрым на чтение: `orc_none` оказался самым медленным из всех, 5.55 с, потому что с диска читается больше байт. Для часто читаемых данных подходит SNAPPY, по умолчанию разумно оставить ZSTD, а GZIP имеет смысл только для холодных архивов. Разница между cold и warm прогоном небольшая, потому что объём данных мал и файлы уже лежат в кэше.

К цифрам по времени записи нужно относиться с осторожностью. В обоих батчах таблица с кодеком ZSTD записывалась первой сразу после перезапуска Trino и оказалась быстрее всех остальных, 52–53 с против 70–130 с. Вероятная причина в состоянии JVM сразу после старта, без накопленной нагрузки, а не в свойствах самого кодека. Контролируемый замер, где каждая таблица создавалась после отдельного перезапуска, сделан выше, в сравнении GZIP и ZSTD, и там результат совпал с ожиданиями. На машине с 8 ГБ RAM Trino уже падал по нехватке памяти (раздел 1), а несколько контейнеров работают одновременно — это добавляет шум в измерения.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

**Зачем нужен lakehouse, а не обычная БД.** Обычная БД хранит данные и выполняет вычисления на одном движке, поэтому масштабирование обходится дорого, а данные доступны только через саму БД. Lakehouse разделяет хранение и вычисления: данные лежат в открытых файлах parquet/orc в дешёвом объектном хранилище, а любой движок читает их через открытый каталог, например Iceberg. Это дешевле на больших объёмах, не привязывает к одному движку и при этом даёт SQL и транзакции, которых не было у обычного data lake.

**Schema evolution на Silver.** Выполнена команда `ALTER TABLE dim_customer ADD COLUMN loyalty_tier varchar`. У всех существующих 150 000 строк новая колонка стала `NULL`, старые файлы при этом не переписывались: Iceberg обновил только схему в метаданных. Сам `ALTER` не создал новый снапшот, изменение схемы в Iceberg — чисто метаданная операция, не версия данных. После вставки новой строки с заполненным значением `loyalty_tier` появился новый снапшот с операцией `append`. Старые и новые файлы с разными схемами читаются совместно, без простоя.

**Time travel и восстановление.** После вставки тестовой строки (`custkey=999999`) в таблице стало два снапшота. Запрос `SELECT count(*) ... FOR VERSION AS OF <старый snapshot_id> WHERE custkey=999999` вернул 0, хотя в текущей версии строка есть (`count=1`). Затем выполнена команда `ALTER TABLE ... EXECUTE rollback_to_snapshot(snapshot_id => ...)`, после которой таблица вернулась к исходным 150 000 строкам, а тестовая строка исчезла. Такой откат нужен при восстановлении после ошибочной вставки, без обращения к внешнему резервному копированию.

### 6.2. Подключить инструмент к lakehouse

Выбран Metabase. Роли движка и каталога уже закрыты Trino и Lakekeeper, поэтому из оставшихся вариантов BI-инструмент подходит лучше всего: один контейнер, собственная база метаданных, простое развёртывание.

```bash
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase
```

Вторая команда нужна, чтобы Metabase видел Trino по имени `trino` в общей сети. Без неё `host.docker.internal` ведёт не туда, и порт 8080 недостижим.

Подключение к lakehouse выполнено через REST API Metabase, без ручной настройки в интерфейсе:

```bash
curl -X POST http://localhost:3000/api/setup -d '{"token": "...", "user": {...}}'

curl -X POST http://localhost:3000/api/database \
  -H "X-Metabase-Session: <session>" \
  -d '{"engine": "starburst", "name": "Lakehouse Bronze (Trino)",
       "details": {"host": "trino", "port": 8080, "catalog": "bronze",
                    "schema": "lakehouse", "user": "trino", "ssl": false}}'
```

Metabase обнаружил все 4 таблицы Bronze-слоя и успешно выполнил тестовый запрос. Цепочка Metabase → Trino → Lakekeeper → MinIO работает.

При настройке возникла проблема: драйвер `presto-jdbc`, который документация Metabase рекомендует для Trino, возвращал ошибку авторизации («X-Trino-User must be sent») независимо от настроек. Решил её переход на драйвер `starburst` — тот же протокол, но без этой ошибки.

## 7. Выводы

На практике медальон — это не три копии одних данных, а разделение обязанностей между слоями. Bronze хранит данные без изменений. Silver — единственное место с бизнес-фильтрами и обогащением: джойн с nation, фильтр по кварталу и признаку возврата. Gold выполняет только группировку, потому что вся сложность уже решена на нижних слоях. Отсюда и распределение веса: Gold занимает около 3 КБ, а основную массу, 69 из примерно 112 МБ, несёт `raw_lineitem` в слое Bronze. Детализированные данные хранятся внизу, агрегат наверху, и это ожидаемо.

По кодекам: на данных типа `lineitem` ZSTD и GZIP сжимают почти одинаково, но ZSTD заметно быстрее пишет и читает. Выбор ZSTD по умолчанию в Trino обоснован для такого рода данных. GZIP стоит применять только для холодных, редко читаемых архивов.

Метаданные Iceberg незначительны на фоне сотен МБ данных: манифесты занимают всего 8–9 КБ. Кроме этого, в работе встретились два момента, которых не видно из таблиц. Объём памяти стенда реально ограничивает возможности — Trino падал по нехватке памяти, и масштаб `sfN` нужно подбирать под ресурсы конкретной машины, а не только по общим рекомендациям. А рекомендованный документацией драйвер BI-инструмента не гарантирует совместимость с конкретной версией движка, это лучше проверять на практике, а не полагаться только на документацию.
