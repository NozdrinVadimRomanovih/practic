| Масштаб `sfN` | sf1 |
| Почему выбрал такой масштаб | Стенд работает на машине с 8 ГБ RAM, 50 ГБ свободного диска и 8 CPU. Docker Desktop выделяет контейнерам в сумме около 3.8 ГБ RAM. Бенчмарк форматов и кодеков (раздел 5) требует хранить 8 таблиц одновременно в бакете `bench`. На `sf10` это 15–55 ГБ и риск нехватки памяти у Trino. На этом масштабе весь бенчмарк (запись 8 таблиц и 16 замеров) укладывается в несколько минут и не роняет контейнер. При этом данных достаточно, чтобы разница между кодеками была видна, а не терялась в шуме, как на `tiny`. |

## 2. Поднятые сервисы — и почему именно они

Состояние сервисов проверено командой `docker compose ps` — все сервисы в статусе `healthy`.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO (образ `pgsty/silo`) | S3-совместимое объектное хранилище. Здесь физически лежат parquet/orc-файлы всех слоёв | Открытый код и полная совместимость с S3 API — ведёт себя так же, как облачное хранилище (AWS S3/GCS), но бесплатно и без аккаунта. Официальные образы `minio/minio` и `quay.io/minio/minio` сняты с публичных реестров в 2026 году. `pgsty/silo` — поддерживаемый drop-in форк с тем же API, портами и переменными окружения, поэтому замена потребовала только смены имени образа |
| PostgreSQL 17 | БД, в которой Lakekeeper хранит метаданные каталога: список warehouse, таблиц, снапшотов | Рекомендован документацией Lakekeeper как backend для Iceberg REST-каталогов. Надёжен и даёт простой health-check (`pg_isready`) для docker-compose |
| Lakekeeper | Iceberg REST Catalog. Хранит метаданные таблиц (файлы, снапшоты, схемы) отдельно от самих данных | Открытая реализация спецификации Iceberg REST Catalog. К такому каталогу подключается любой совместимый движок (Trino, Spark, DuckDB) без проприетарной интеграции — в отличие от AWS Glue. Поддерживает несколько независимых `warehouse`. Это использовано для физического разделения слоёв медальона: отдельный warehouse на `bronze`, `silver`, `gold` и `bench`, плюс `demo` из базового гайда |
| Trino | SQL-движок. Берёт метаданные у Lakekeeper, читает и пишет parquet/orc в MinIO | Один SQL-диалект сразу над всеми каталогами и слоями через трёхчастные имена `catalog.schema.table`. Встроенный коннектор `tpch` генерирует тестовые данные без внешней загрузки. Системные таблицы Iceberg (`$files`, `$snapshots`, `$manifests`, `$properties`) дают все метрики для отчёта без похода в консоль MinIO |
| Metabase | BI-инструмент поверх Bronze-слоя (раздел 6.2) | Один контейнер, своя встроенная БД метаданных (H2), поднимается одной командой `docker run`, поддерживает подключение к Trino по JDBC |

### Скрипты, которыми поднимался стек

Базовый стек (MinIO, PostgreSQL, Lakekeeper, Trino) поднимается одной командой из `docker-compose.yml` в корне репозитория:

```bash
docker compose up -d
```

Исходный `docker-compose.yml` из гайда не содержал слоёв медальона и BI-инструмента. Файл дополнен тремя вещами:

- сервис `lakekeeper-warehouse-medallion` — регистрирует четыре дополнительных warehouse (`bronze`, `silver`, `gold`, `bench`) через REST API Lakekeeper, по тому же принципу, что штатный `lakekeeper-warehouse`;
- сервис `metabase`;
- расширенный `minio-init` — создаёт бакеты `bronze`, `silver`, `gold`, `bench` вместе со штатным `warehouse`.

После этих изменений весь стек, включая медальон и BI, поднимается той же командой `docker compose up -d`. Catalog-файлы Trino (`catalog/bronze.properties`, `catalog/silver.properties`, `catalog/gold.properties`, `catalog/bench.properties`, `catalog/tpch.properties`) сделаны по образцу `catalog/lakekeeper.properties` из базового гайда. В каждом изменена только строка `iceberg.rest-catalog.warehouse`.

Команды, которые фактически выполнялись после того, как `docker compose up -d` поднял базовую часть стека:

```bash
# создание бакетов bronze/silver/gold/bench в MinIO
docker run --rm --entrypoint /bin/sh --add-host host.docker.internal:host-gateway \
  pgsty/mc:latest -c "mc alias set m http://host.docker.internal:9000 minioadmin minioadmin && \
  mc mb --ignore-existing m/bronze && mc mb --ignore-existing m/silver && \
  mc mb --ignore-existing m/gold && mc mb --ignore-existing m/bench"

# регистрация warehouse bronze/silver/gold/bench в Lakekeeper
for wh in bronze silver gold bench; do
  curl -X POST http://localhost:8181/management/v1/warehouse \
    -H "Content-Type: application/json" -d @create-warehouse-$wh.json
done

docker restart lakehouse-trino-1   # перечитать новые catalog/*.properties

# подключение BI-инструмента
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase
```

## 3. Разбор запроса — какие данные нужны

Вариант 2 — Q10 «Returned Item Reporting»: топ-20 клиентов по выручке от возвращённых позиций (`returnflag = 'R'`) за четвёртый квартал 1993 года.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `customer` | `custkey`, `name`, `acctbal`, `address`, `phone`, `comment`, `nationkey` | джойн с `orders` по `custkey`; джойн с `nation` по `nationkey`; `name`, `acctbal`, `address`, `phone`, `comment` идут в вывод без изменений |
| `orders` | `orderkey`, `custkey`, `orderdate` | фильтр `orderdate >= 1993-10-01 AND orderdate < 1994-01-01`; джойн с `customer` по `custkey` и с `lineitem` по `orderkey` |
| `lineitem` | `orderkey`, `extendedprice`, `discount`, `returnflag` | фильтр `returnflag = 'R'`; агрегат `sum(extendedprice * (1 - discount))` как `revenue` |
| `nation` | `nationkey`, `name` | джойн с `customer` по `nationkey`; `name` выводится как `nation` |

## 4. Медальон — решения по каждому слою

Формат во всех таблицах — `PARQUET`. Кодек сжатия не переопределялся явно и равен значению по умолчанию для Iceberg-коннектора Trino (`ZSTD`). Контролируемое сравнение `GZIP` и `ZSTD` — отдельно, в разделе 5. Партиционирование не задавалось ни в одной таблице: самая крупная (`raw_lineitem`) занимает около 69 МБ в одном файле на `sf1`, и партиционирование такого объёма только добавило бы накладные расходы на планирование запроса без выигрыша в скорости. Эффект от партиционирования заметен начиная с объёмов в сотни МБ — единицы ГБ на партицию. Количество строк и вес таблиц получены через `SELECT count(*)` и системную таблицу Iceberg `$files` (`sum(file_size_in_bytes)`; 1 МБ принят равным 1 000 000 байт).

## 5. Тесты производительности

### Сравнение кодеков GZIP и ZSTD на Bronze

Для сравнения созданы две копии таблицы `bronze.raw_lineitem`, отличающиеся только параметром `compression_codec`. Обе таблицы создавались сразу после перезапуска Trino, чтобы состояние JVM не влияло на результат. Запрос для замера времени — тот же джойн и фильтр, что в Q10: `raw_orders` ⋈ `raw_lineitem_<codec>`, условие `returnflag = 'R'` и четвёртый квартал 1993 года, топ-20 по выручке.

| Сжатие на Bronze | Время запроса, с | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | 6.48 | 65.18 | Сжимает почти так же, как ZSTD — разница в размере меньше 1%. Но заметно медленнее и на запись (22.63 с), и на чтение. На `lineitem` (в основном числовые и decimal-колонки) эта цена по CPU не окупается |
| ZSTD | 4.14 | 65.68 | Быстрее GZIP на запись (20.09 с, разница около 11%) и на запрос (разница около 36%), при почти том же размере на диске. Bronze читается при каждом пересчёте Silver, поэтому ZSTD — более обоснованный выбор |

Время запроса измерялось командой `time docker exec lakehouse-trino-1 trino --execute "..."` — проще, чем `system.runtime.queries`, для разовых замеров.

**Вывод по сравнению.** На данных типа `lineitem` GZIP не даёт преимущества, которое оправдало бы лишнюю нагрузку на CPU. ZSTD даёт похожее сжатие при меньшем времени записи и чтения. Отсюда общая рекомендация: GZIP — только для данных, которые пишутся один раз и читаются редко (холодный архив).

### Дополнительный бенчмарк форматов и кодеков: Parquet/ORC × 4 кодека

Кроме обязательного сравнения проведён более полный бенчмарк: восемь комбинаций формата (Parquet, ORC) и кодека (NONE, SNAPPY, GZIP, ZSTD) на полной таблице `tpch.sf1.lineitem` (6 001 215 строк). Таблицы лежат в отдельной схеме `bench.lakehouse` со своим warehouse и бакетом MinIO. Каждая создана запросом `CREATE TABLE ... WITH (format = ..., compression_codec = ...) AS SELECT * FROM tpch.sf1.lineitem`. Размер и число файлов — через `$files`, время записи — через `time docker exec ... trino --execute`. Скорость агрегации — через запрос TPC-H Q1 (`GROUP BY returnflag, linestatus`), дважды: «холодный» прогон сразу после `docker restart lakehouse-minio-1 lakehouse-trino-1` и «тёплый» прогон сразу за ним.

| Вариант | Размер, МБ | Файлов | Время записи, с | Агрегация cold, с | Агрегация warm, с |
|---|---|---|---|---|---|
| parquet_none | 356.65 | 4 | 80.31 | 3.80 | 3.17 |
| parquet_snappy | 199.36 | 4 | 70.82 | 3.38 | 3.46 |
| parquet_gzip | 141.71 | 4 | 72.51 | 2.73 | 2.61 |
| parquet_zstd | 148.16 | 4 | 52.94 | 4.54 | 2.91 |
| orc_none | 452.62 | 4 | 127.68 | 5.55 | 5.45 |
| orc_snappy | 221.43 | 4 | 120.61 | 3.20 | 3.35 |
| orc_gzip | 149.65 | 4 | 117.44 | 2.80 | 3.05 |
| orc_zstd | 161.19 | 4 | 52.82 | 3.92 | 3.13 |

Метаданные каждой таблицы — один манифест-файл текущего снапшота размером 8–9 КБ (например, 8833 байта у `parquet_zstd`, 8515 байт у `orc_none`) против 142–453 МБ данных. Метаданные составляют тысячные доли процента от объёма данных — накладные расходы каталога Iceberg здесь не имеют практического значения.

**Анализ по вопросам методики:**

1. *Размер.* Сильнее всего сжал GZIP в обоих форматах: у ORC `NONE → GZIP` даёт −66.9%, у Parquet −60.3%. ZSTD отстал незначительно (ORC −64.4%, Parquet −58.5%). При одинаковом кодеке ORC стабильно крупнее Parquet (для `NONE`: 452.62 МБ против 356.65 МБ) — на плоской таблице без вложенных структур у ORC нет того преимущества, которое он обычно показывает на сложных схемах.
2. *Время записи.* В этом прогоне GZIP оказался не медленнее, а на одном из форматов даже быстрее NONE — это противоречит ожидаемой закономерности. Причина не в кодеке, а в особенностях замера — объяснение ниже, в разделе про ограничения методики.
3. *Скорость чтения.* NONE не был самым быстрым на чтение ни в одном из форматов: `orc_none` показал наибольшее время агрегации — 5.55 с на холодном прогоне, хотя распаковывать ему нечего. Причина — с диска и из MinIO читается кратно больше байт (452 МБ против 142–221 МБ у сжатых вариантов). На этом объёме время определяет объём I/O, а не CPU на распаковку.
4. *Сводный компромисс.* Для горячих данных, которые читают часто и параллельно, обоснован SNAPPY — минимальная нагрузка на CPU при чтении. ZSTD обоснован как дефолт для данных без явной причины отклоняться — это подтверждает и сравнение на Bronze выше. GZIP имеет смысл только там, где место на диске дороже CPU и данные читаются редко. В этом эксперименте GZIP не дал заметного выигрыша в размере против ZSTD, но стабильно уступал по скорости записи при контролируемом замере.
5. *Метаданные и кэширование.* Манифесты (8–9 КБ) меньше данных (142–453 МБ) на несколько порядков. Разница между холодным и тёплым прогоном здесь оказалась небольшой и не всегда однозначной — объяснение ниже.

**Ограничения методики данного бенчмарка.** Часть результатов нужно читать с осторожностью — они не являются безусловной характеристикой кодеков:

- В обоих батчах (Parquet и ORC) таблица с ZSTD создавалась первой сразу после перезапуска Trino и показала заметно меньшее время записи (52.9 с и 52.8 с против 70–130 с у остальных). Вероятная причина — чистое состояние JVM без конкуренции за ресурсы сразу после запуска, а не свойства самого кодека. Для честного замера нужен перезапуск Trino перед записью каждой отдельной таблицы. Именно так сделано в сравнении GZIP/ZSTD выше — и там результат (ZSTD быстрее GZIP) совпал с теорией.
- Памяти на стенде немного: 8 ГБ RAM, лимит контейнера Trino около 3.8 ГБ. Это и привело к аварийному завершению Trino, описанному в разделе 1. Фоновая нагрузка от других контейнеров (Lakekeeper, MinIO, PostgreSQL, Metabase) добавляет шум в замеры времени.
- На `sf1` файлы (142–453 МБ) целиком попадают в страничный кэш ОС уже после одного обращения. Поэтому разница между холодным и тёплым прогоном на загруженной машине частично тонет в фоновом шуме. Это не отменяет правило «тёплый прогон быстрее» — просто показывает его предел на небольших объёмах. Для чистого измерения нужен масштаб не меньше `sf10` и изолированная машина.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Обычная реляционная БД (PostgreSQL, MySQL) хранит и считает на одном движке. Масштабировать её вширь дорого, а данные доступны только через саму БД, в её собственном формате. Lakehouse разделяет хранение и вычисления: данные лежат в открытых форматах (parquet/orc) в объектном S3-хранилище, а любой движок (Trino, Spark, DuckDB) читает их через открытый каталог вроде Iceberg. Это дешевле на больших объёмах — платишь за объём в объектном хранилище, а не в проприетарной БД. Это даёт независимость от одного движка. И при этом есть SQL и ACID-транзакции, которых не было у классического data lake — там данные лежали просто файлами, без каталога и без транзакций |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | На `silver.lakehouse.dim_customer` выполнена команда `ALTER TABLE ... ADD COLUMN loyalty_tier varchar`. Результат: (1) у всех существующих 150 000 строк новая колонка стала `NULL` (проверено условием `loyalty_tier IS NULL`), а старые parquet-файлы не переписывались — Iceberg обновил только схему в метаданных; (2) сам `ALTER TABLE ADD COLUMN` не создал новый снапшот в `$snapshots` — до и после изменения схемы id снапшота один и тот же, значит изменение схемы в Iceberg чисто метаданное; (3) после вставки новой строки со значением `loyalty_tier = 'GOLD'` появился новый снапшот с операцией `append`, и в новой строке колонка уже заполнена. Итог: файлы со старой и новой схемой читаются вместе, без переписывания старых данных и без простоя |
| Пример скрипта восстановления данных из снапшота (time travel) | После вставки тестовой строки (`custkey = 999999`) в `dim_customer` стало два снапшота. Восстановление: `SELECT count(*) FROM silver.lakehouse.dim_customer WHERE custkey=999999` — возвращает 1 (строка есть в текущей версии). `SELECT count(*) FROM silver.lakehouse.dim_customer FOR VERSION AS OF 5376283007035176433 WHERE custkey=999999` — возвращает 0 (строки не было в снапшоте до вставки). Затем `ALTER TABLE silver.lakehouse.dim_customer EXECUTE rollback_to_snapshot(snapshot_id => 5376283007035176433)` — после этого `SELECT count(*) FROM dim_customer` снова даёт 150 000, тестовой строки в таблице нет. Такой откат нужен при ошибочной загрузке или неверной вставке: таблица возвращается к снапшоту до инцидента без обращения к внешнему бэкапу |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Metabase (BI) | Из категорий BI/движок/каталог выбран BI — движок и каталог уже закрыты Trino и Lakekeeper. Metabase — один контейнер, своя встроенная БД метаданных (H2), поднимается одной командой `docker run`, поддерживает протокол Trino |

Скрипты развёртывания:

```bash
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase
```

Вторая команда подключает Metabase к той же docker-сети, где работают Trino, Lakekeeper и MinIO. Без неё Metabase резолвит `host.docker.internal` на внутренний gateway Docker Desktop, с которого нельзя попасть обратно на опубликованный порт 8080. Рабочий способ — обращаться к Trino по DNS-имени сервиса `trino` внутри общей сети `lakehouse_lakehouse`.

Подключение к lakehouse сделано через REST API Metabase, без визуального мастера настройки — для воспроизводимости:

```bash
# создание администратора (одноразово, через setup-token
# из /api/session/properties)
curl -X POST http://localhost:3000/api/setup -d '{"token": "...", "user": {...}}'

# подключение каталога bronze Trino как источника данных
curl -X POST http://localhost:3000/api/database \
  -H "X-Metabase-Session: <session>" \
  -d '{
    "engine": "starburst",
    "name": "Lakehouse Bronze (Trino)",
    "details": {"host": "trino", "port": 8080, "catalog": "bronze", "schema": "lakehouse", "user": "trino", "ssl": false}
  }'
```

Результат: Metabase (`initial_sync_status: complete`) увидел все четыре таблицы Bronze-слоя (`raw_customer`, `raw_orders`, `raw_lineitem`, `raw_nation`) и выполнил через `/api/dataset` тестовый SQL-запрос к `bronze.lakehouse.raw_customer`, получив корректные данные. Цепочка Metabase → Trino → Lakekeeper → MinIO работает.

При настройке нашлась несовместимость: драйвер `presto-jdbc`, который документация Metabase рекомендует для Trino, стабильно возвращал ошибку аутентификации («Authentication failed: ... X-Trino-User must be sent») независимо от значения параметра `user`. Решение — драйвер `starburst`: тот же протокол, но корректно поддерживает текущую схему заголовков аутентификации. На стороне Trino менять ничего не пришлось.

## 7. Выводы

Медальонная архитектура на практике — это не три копии одних данных, а конкретные решения на каждом слое. Bronze хранит источник без изменений и без потерь. Silver — единственное место, где есть бизнес-фильтры и денормализация: джойн с `nation` в `dim_customer`, фильтр по кварталу и признаку возврата в `fct_returned_lineitem`. Gold делает только группировку и суммирование, потому что вся сложность уже решена на нижних слоях. Отсюда резкое уменьшение объёма от слоя к слою: Gold — около 3 КБ на 20 строк, а основной вес медальона (69 МБ из примерно 112 МБ) несёт `raw_lineitem` в Bronze. Это ожидаемо: детализация живёт внизу, агрегат — наверху.

Сравнение кодеков показало, что на `lineitem` (в основном числовые и decimal-колонки) разница в сжатии между ZSTD и GZIP минимальна — меньше процента в контролируемом замере. При этом по скорости записи и чтения ZSTD уверенно выигрывает. Это оправдывает выбор ZSTD как кодека по умолчанию в Iceberg-коннекторе Trino для такого типа данных. GZIP стоит включать только для действительно холодных, редко читаемых архивов, где важен только объём на диске.

Полный бенчмарк восьми комбинаций формата и кодека подтвердил, что метаданные Iceberg (манифесты по 8–9 КБ) пренебрежимо малы на фоне десятков и сотен мегабайт данных — на таких объёмах это не проблема. Отдельно стоит отметить два практических урока, не видных из таблиц. Во-первых, ограниченная память реально уронила Trino при нагрузке, близкой к `sf10`: масштаб тестовых данных нужно подбирать под ресурсы конкретного стенда, а не только по рекомендации гайда. Во-вторых, несовместимость рекомендованного драйвера Metabase с установленной версией Trino показывает, что совместимость BI-инструмента с конкретной версией движка лучше проверять на практике, а не доверять документации вслепую.
