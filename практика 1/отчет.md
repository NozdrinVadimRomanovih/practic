После этого масштаб `sf1` (около 6 млн строк `lineitem`, ~0.7 ГБ в несжатом виде) был выбран как решение, безопасное по памяти и дисковому пространству: весь бенчмарк (запись 8 таблиц и 16 замеров агрегаций) укладывается в несколько минут, при этом объём данных достаточен, чтобы различия между кодеками были измеримыми, а не статистическим шумом, как на масштабе `tiny`. |

## 2. Поднятые сервисы — и почему именно они

Состояние сервисов проверено командой `docker compose ps` — все сервисы находятся в статусе `healthy`.

| Сервис | Роль в стеке | Почему именно он (а не альтернатива) |
|---|---|---|
| MinIO (образ `pgsty/silo`) | S3-совместимое объектное хранилище — физическое расположение parquet/orc-файлов всех слоёв | Открытый исходный код и полная совместимость с S3 API — поведение идентично облачному объектному хранилищу (AWS S3/GCS), но без затрат и необходимости в облачном аккаунте. Официальные образы `minio/minio` и `quay.io/minio/minio` были сняты с публичных реестров в 2026 году; `pgsty/silo` — поддерживаемый drop-in форк с тем же API, портами и переменными окружения, поэтому замена не потребовала изменения команд, только имени образа |
| PostgreSQL 17 | Реляционная БД, в которой Lakekeeper хранит метаданные каталога (состав warehouse, таблиц, снапшотов) | Рекомендуемый в документации Lakekeeper backend для Iceberg REST-каталогов; надёжен и предоставляет простой health-check (`pg_isready`) для docker-compose |
| Lakekeeper | Iceberg REST Catalog — хранит метаданные таблиц (файлы, снапшоты, схемы) отдельно от самих данных | Открытая реализация спецификации Iceberg REST Catalog, к которой может подключиться любой совместимый движок (Trino, Spark, DuckDB) без проприетарной интеграции, в отличие от AWS Glue. Поддерживает несколько независимых `warehouse`, что использовано для физического разделения слоёв медальона (warehouse `bronze`, `silver`, `gold`, `bench` — дополнительно к `demo` из базового гайда) |
| Trino | SQL-движок: обращается к Lakekeeper за метаданными, читает и пишет parquet/orc в MinIO | Единый SQL-диалект поверх всех каталогов и слоёв сразу (трёхчастные имена `catalog.schema.table`); встроенный коннектор `tpch` позволяет генерировать тестовые данные без внешней загрузки; системные таблицы Iceberg (`$files`, `$snapshots`, `$manifests`, `$properties`) дают все метрики для отчёта без обращения к консоли MinIO |
| Metabase | BI-инструмент поверх Bronze-слоя (раздел 6.2) | Разворачивается в одном контейнере, не требует внешней БД для собственных метаданных (встроенная H2), поднимается одной командой `docker run` и поддерживает подключение к Trino по JDBC |

### Скрипты, которыми поднимался стек

Базовый стек (MinIO, PostgreSQL, Lakekeeper, Trino) поднимается одной командой из файла `docker-compose.yml`, находящегося в корне репозитория:

```bash
docker compose up -d
```

Исходный `docker-compose.yml` из гайда не содержал ни слоёв медальона, ни BI-инструмента. Файл был дополнен следующими изменениями:

- сервис `lakekeeper-warehouse-medallion` — регистрирует четыре дополнительных warehouse (`bronze`, `silver`, `gold`, `bench`) через REST API Lakekeeper, по тому же принципу, что штатный сервис `lakekeeper-warehouse`;
- сервис `metabase`;
- расширенный сервис `minio-init`, который дополнительно создаёт бакеты `bronze`, `silver`, `gold`, `bench` вместе со штатным бакетом `warehouse`.

После внесения этих изменений весь стек, включая слои медальона и BI-инструмент, поднимается той же единственной командой `docker compose up -d`. Catalog-файлы Trino (`catalog/bronze.properties`, `catalog/silver.properties`, `catalog/gold.properties`, `catalog/bench.properties`, `catalog/tpch.properties`) созданы по образцу `catalog/lakekeeper.properties` из базового гайда; в каждом изменена только строка `iceberg.rest-catalog.warehouse`.

Ниже приведены команды, фактически выполненные после того, как `docker compose up -d` поднял базовую часть стека:

```bash
# создание бакетов bronze/silver/gold/bench в MinIO
docker run --rm --entrypoint /bin/sh --add-host host.docker.internal:host-gateway \
  pgsty/mc:latest -c "mc alias set m http://host.docker.internal:9000 minioadmin minioadmin && \
  mc mb --ignore-existing m/bronze && mc mb --ignore-existing m/silver && \
  mc mb --ignore-existing m/gold && mc mb --ignore-existing m/bench"

# регистрация warehouse bronze/silver/gold/bench в Lakekeeper
for wh in bronze silver gold bench; do
  curl -X POST http://localhost:8181/management/v1/warehouse \
    -H "Content-Type: application/json" -d @create-warehouse-$wh.json
done

docker restart lakehouse-trino-1   # перечитать новые catalog/*.properties

# подключение BI-инструмента
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase
```

## 3. Разбор запроса — какие данные нужны

Вариант 2 — Q10 «Returned Item Reporting»: топ-20 клиентов по выручке от возвращённых позиций (`returnflag = 'R'`) за четвёртый квартал 1993 года.

| Таблица TPC-H | Нужные колонки | Что запрос с ними делает (фильтр / джойн / агрегат / вывод) |
|---|---|---|
| `customer` | `custkey`, `name`, `acctbal`, `address`, `phone`, `comment`, `nationkey` | джойн с `orders` по `custkey`; джойн с `nation` по `nationkey`; колонки `name`, `acctbal`, `address`, `phone`, `comment` выводятся без изменений |
| `orders` | `orderkey`, `custkey`, `orderdate` | фильтр `orderdate >= 1993-10-01 AND orderdate < 1994-01-01` (четвёртый квартал 1993 года); джойн с `customer` по `custkey` и с `lineitem` по `orderkey` |
| `lineitem` | `orderkey`, `extendedprice`, `discount`, `returnflag` | фильтр `returnflag = 'R'`; агрегат `sum(extendedprice * (1 - discount))` как `revenue` |
| `nation` | `nationkey`, `name` | джойн с `customer` по `nationkey`; колонка `name` выводится как `nation` |

## 4. Медальон — решения по каждому слою

Формат во всех таблицах — `PARQUET`; кодек сжатия явно не переопределялся и соответствует значению по умолчанию для Iceberg-коннектора Trino (`ZSTD`) — контролируемое сравнение кодеков `GZIP` и `ZSTD` выделено отдельно в разделе 5. Партиционирование не задавалось ни в одной таблице: наибольшая по объёму таблица (`raw_lineitem`) занимает около 69 МБ в одном файле на масштабе `sf1`, и партиционирование такого объёма добавило бы накладные расходы на планирование запроса без выигрыша в скорости — эффект от партиционирования становится заметен начиная с объёмов в сотни МБ — единицы ГБ на партицию. Количество строк и вес таблиц получены через `SELECT count(*)` и системную таблицу Iceberg `$files` (`sum(file_size_in_bytes)`; 1 МБ принят равным 1 000 000 байт).

## 5. Тесты производительности

### Сравнение кодеков GZIP и ZSTD на Bronze

Для контролируемого сравнения созданы две отдельные копии таблицы `bronze.raw_lineitem`, отличающиеся только параметром `compression_codec`; обе таблицы создавались сразу после перезапуска Trino, чтобы исключить влияние состояния JVM на результат. Запрос для замера времени — тот же джойн и фильтр, что используются в варианте Q10 (`raw_orders` ⋈ `raw_lineitem_<codec>`, условие `returnflag = 'R'` и четвёртый квартал 1993 года, топ-20 по выручке).

| Сжатие на Bronze | Время запроса, с | Размер Bronze, МБ | Твой вывод (что лучше и почему) |
|---|---|---|---|
| GZIP | 6.48 | 65.18 | Сжимает практически так же, как ZSTD (разница в размере менее 1%), однако заметно медленнее как на запись (22.63 с), так и на чтение. На таблице `lineitem`, состоящей в основном из числовых и decimal-колонок, более высокая стоимость по CPU не компенсируется выигрышем в размере |
| ZSTD | 4.14 | 65.68 | Быстрее GZIP на запись (20.09 с, разница около 11%) и быстрее на выполнение запроса (разница около 36%) при практически идентичном размере на диске. Для данных, которые читаются неоднократно — а Bronze читается при каждом пересчёте слоя Silver — ZSTD является более обоснованным выбором |

Время запроса измерялось командой `time docker exec lakehouse-trino-1 trino --execute "..."`, что по смыслу эквивалентно обращению к `system.runtime.queries`, но проще для однократных замеров.

**Вывод по сравнению.** На данных типа `lineitem` кодек GZIP не даёт преимущества, которое оправдало бы дополнительную нагрузку на процессор; ZSTD обеспечивает сопоставимое сжатие при меньшем времени записи и чтения, что соответствует общей рекомендации использовать GZIP только для данных, записываемых однократно и читаемых редко (холодный архив).

### Дополнительный бенчмарк форматов и кодеков: Parquet/ORC × 4 кодека

В дополнение к обязательному сравнению проведён более полный бенчмарк: восемь комбинаций формата (Parquet, ORC) и кодека (NONE, SNAPPY, GZIP, ZSTD) на полной таблице `tpch.sf1.lineitem` (6 001 215 строк), размещённых в отдельной схеме `bench.lakehouse` со своим warehouse и бакетом MinIO. Каждая таблица создана запросом вида `CREATE TABLE ... WITH (format = ..., compression_codec = ...) AS SELECT * FROM tpch.sf1.lineitem`. Размер и количество файлов получены через системную таблицу `$files`, время записи — через `time docker exec ... trino --execute`, скорость агрегации — через классический запрос TPC-H Q1 (`GROUP BY returnflag, linestatus`), выполненный дважды: «холодный» прогон сразу после `docker restart lakehouse-minio-1 lakehouse-trino-1` и «тёплый» прогон непосредственно следом.

| Вариант | Размер, МБ | Файлов | Время записи, с | Агрегация cold, с | Агрегация warm, с |
|---|---|---|---|---|---|
| parquet_none | 356.65 | 4 | 80.31 | 3.80 | 3.17 |
| parquet_snappy | 199.36 | 4 | 70.82 | 3.38 | 3.46 |
| parquet_gzip | 141.71 | 4 | 72.51 | 2.73 | 2.61 |
| parquet_zstd | 148.16 | 4 | 52.94 | 4.54 | 2.91 |
| orc_none | 452.62 | 4 | 127.68 | 5.55 | 5.45 |
| orc_snappy | 221.43 | 4 | 120.61 | 3.20 | 3.35 |
| orc_gzip | 149.65 | 4 | 117.44 | 2.80 | 3.05 |
| orc_zstd | 161.19 | 4 | 52.82 | 3.92 | 3.13 |

Объём метаданных для каждой из этих таблиц составил один манифест-файл текущего снапшота размером 8–9 КБ (например, 8833 байта для `parquet_zstd` и 8515 байт для `orc_none`) против 142–453 МБ данных — метаданные составляют тысячные доли процента от объёма данных, и накладные расходы каталога Iceberg на этом объёме не имеют практического значения.

**Анализ по вопросам методики:**

1. *Размер.* Сильнее всего сжал GZIP в обоих форматах (у ORC переход `NONE → GZIP` даёт уменьшение на 66.9%, у Parquet — на 60.3%), ZSTD отстал незначительно (ORC −64.4%, Parquet −58.5%). При одинаковом кодеке ORC стабильно крупнее Parquet (например, для `NONE`: 452.62 МБ против 356.65 МБ) — на плоской таблице без вложенных структур у формата ORC отсутствует преимущество, которое он обычно демонстрирует на сложных схемах.
2. *Время записи.* В этом прогоне GZIP оказался не медленнее, а на одном из форматов даже быстрее варианта NONE, что противоречит ожидаемой закономерности. Причина заключается не в свойствах кодека, а в особенностях замера — пояснение приведено в подразделе об ограничениях методики ниже.
3. *Скорость чтения.* Вариант NONE не был самым быстрым на чтение ни в одном из форматов (вариант `orc_none` показал наибольшее время агрегации — 5.55 с на холодном прогоне), несмотря на отсутствие затрат на распаковку — поскольку с диска и из MinIO считывается кратно больший объём байт (452 МБ против 142–221 МБ у сжатых вариантов), и на этом объёме данных время определяется объёмом операций ввода-вывода, а не затратами CPU на распаковку.
4. *Сводный компромисс.* Для часто читаемых и одновременно запрашиваемых («горячих») данных обоснован выбор SNAPPY — минимальная нагрузка на CPU при чтении при приемлемом сжатии. ZSTD обоснован как кодек по умолчанию для данных без явной причины для отклонения от этого выбора, что подтверждается результатом контролируемого сравнения на Bronze. GZIP целесообразен только в случаях, когда стоимость дискового пространства существенно выше стоимости процессорного времени и данные читаются редко (архивный, холодный слой); в проведённом эксперименте GZIP не дал ощутимого выигрыша в размере по сравнению с ZSTD, но стабильно уступал по скорости записи при контролируемом замере.
5. *Метаданные и кэширование.* Манифесты (8–9 КБ) меньше объёма данных (142–453 МБ) на несколько порядков. Разница между холодным и тёплым прогоном в данном эксперименте оказалась небольшой и не всегда однозначной — объяснение приведено ниже.

**Ограничения методики данного бенчмарка.** Часть результатов требует осторожной интерпретации и не должна приниматься за безусловную характеристику кодеков:

- В обоих батчах (Parquet и ORC) таблица с кодеком ZSTD создавалась первой сразу после перезапуска Trino и показала заметно меньшее время записи (52.9 с и 52.8 с против 70–130 с у остальных вариантов того же батча). Вероятная причина — состояние JVM без накопленной конкуренции за ресурсы непосредственно после запуска, а не свойства самого кодека. Для полностью изолированного замера требовался бы перезапуск Trino перед записью каждой отдельной таблицы; именно такой подход применён в контролируемом сравнении GZIP/ZSTD выше, и его результат (ZSTD быстрее GZIP) соответствует теоретическим ожиданиям.
- Ограниченный объём памяти стенда (8 ГБ RAM, лимит контейнера Trino около 3.8 ГБ) привёл к документированному в разделе 1 аварийному завершению Trino по нехватке памяти; фоновая нагрузка от одновременно работающих контейнеров (Lakekeeper, MinIO, PostgreSQL, Metabase) добавляет дополнительный шум в измерения времени.
- На масштабе `sf1` файлы данных (142–453 МБ) полностью помещаются в страничный кэш операционной системы уже после одного обращения, из-за чего разница между холодным и тёплым прогоном на загруженной машине частично тонет в фоновом шуме. Это не противоречит общему принципу «тёплый прогон быстрее», но демонстрирует предел его применимости на небольших объёмах данных; для методически чистого измерения требуется масштаб не менее `sf10` и изолированная вычислительная среда.

## 6. Часть 2 — осмысление и работа с инструментами

### 6.1. Понять и объяснить

| Вопрос | Твой ответ |
|---|---|
| Зачем нужны большие данные и lakehouse (а не обычная БД/хранилище)? | Традиционная реляционная БД (PostgreSQL, MySQL) совмещает хранение и вычисления на одном движке — горизонтальное масштабирование обходится дорого, а данные доступны только через саму БД, в её внутреннем формате. Архитектура lakehouse разделяет хранение (объектное S3-совместимое хранилище, данные в открытых форматах parquet/orc) и вычисления (любой движок — Trino, Spark, DuckDB — может обращаться к тем же файлам через открытый каталог, например Iceberg). Такое разделение снижает стоимость хранения больших объёмов (оплата за объём в объектном хранилище, а не в проприетарной БД), обеспечивает независимость от конкретного вычислительного движка и при этом предоставляет SQL-интерфейс и ACID-транзакции, которых не было у классических data lake, где данные хранились как обычные файлы без каталога и без транзакционных гарантий |
| Пример schema evolution на Silver: добавил/переименовал колонку — что произошло? | На таблице `silver.lakehouse.dim_customer` выполнена команда `ALTER TABLE ... ADD COLUMN loyalty_tier varchar`. Наблюдения: (1) у всех существующих 150 000 строк новая колонка приняла значение `NULL` (проверено условием `loyalty_tier IS NULL`), при этом ранее записанные parquet-файлы не были перезаписаны — Iceberg обновил только схему в метаданных; (2) выполнение `ALTER TABLE ADD COLUMN` не привело к созданию нового снапшота в системной таблице `$snapshots` — до и после изменения схемы в таблице снапшотов присутствует один и тот же идентификатор, что подтверждает чисто метаданный характер изменения схемы в Iceberg; (3) после вставки новой строки со значением `loyalty_tier = 'GOLD'` в таблице снапшотов появился новый снапшот с типом операции `append`, и новая строка содержит заполненное значение в добавленной колонке. Таким образом, файлы со старой и новой схемой читаются совместно без необходимости переписывания исторических данных и без простоя |
| Пример скрипта восстановления данных из снапшота (time travel) | После вставки тестовой строки (`custkey = 999999`) в таблице `dim_customer` образовалось два снапшота. Восстановление выполнено следующей последовательностью команд: `SELECT count(*) FROM silver.lakehouse.dim_customer WHERE custkey=999999` возвращает 1 (строка присутствует в текущей версии); `SELECT count(*) FROM silver.lakehouse.dim_customer FOR VERSION AS OF 5376283007035176433 WHERE custkey=999999` возвращает 0 (строки не было в снапшоте, предшествующем вставке); далее выполнена команда `ALTER TABLE silver.lakehouse.dim_customer EXECUTE rollback_to_snapshot(snapshot_id => 5376283007035176433)`, после которой `SELECT count(*) FROM dim_customer` возвращает исходные 150 000 строк, а тестовая строка отсутствует в текущей версии таблицы. Такая процедура применима при восстановлении после ошибочной загрузки или некорректной вставки данных: таблица откатывается к снапшоту, предшествующему инциденту, без обращения к внешнему резервному копированию |

### 6.2. Подключить инструмент к lakehouse

| Инструмент | Почему выбрал именно его |
|---|---|
| Metabase (BI) | Из предложенных категорий (BI, движок, каталог) выбран BI-инструмент, поскольку роли движка и каталога уже закрыты Trino и Lakekeeper соответственно. Metabase разворачивается в одном контейнере, не требует отдельной БД для собственных метаданных (использует встроенную H2), поднимается единственной командой `docker run` и имеет готовую поддержку протокола Trino |

Скрипты развёртывания:

```bash
docker run -d --name metabase -p 3000:3000 metabase/metabase:latest
docker network connect lakehouse_lakehouse metabase
```

Вторая команда подключает контейнер Metabase к той же docker-сети, в которой работают Trino, Lakekeeper и MinIO. Без этого шага Metabase резолвит `host.docker.internal` на внутренний gateway Docker Desktop, с которого недостижим опубликованный порт 8080; рабочий способ — обращение к Trino по DNS-имени сервиса `trino` внутри общей сети `lakehouse_lakehouse`.

Подключение к lakehouse выполнено через REST API Metabase, без использования визуального мастера настройки, для обеспечения воспроизводимости:

```bash
# создание администратора (одноразовая операция, с использованием setup-token
# из эндпойнта /api/session/properties)
curl -X POST http://localhost:3000/api/setup -d '{"token": "...", "user": {...}}'

# подключение каталога bronze Trino как источника данных
curl -X POST http://localhost:3000/api/database \
  -H "X-Metabase-Session: <session>" \
  -d '{
    "engine": "starburst",
    "name": "Lakehouse Bronze (Trino)",
    "details": {"host": "trino", "port": 8080, "catalog": "bronze", "schema": "lakehouse", "user": "trino", "ssl": false}
  }'
```

Результат проверки: Metabase (значение `initial_sync_status` равно `complete`) обнаружил все четыре таблицы Bronze-слоя (`raw_customer`, `raw_orders`, `raw_lineitem`, `raw_nation`) и успешно выполнил через эндпойнт `/api/dataset` тестовый SQL-запрос к таблице `bronze.lakehouse.raw_customer`, получив корректные данные. Тем самым подтверждена работоспособность всей цепочки: Metabase → Trino → Lakekeeper → MinIO.

В процессе настройки обнаружена несовместимость: драйвер `presto-jdbc`, рекомендованный документацией Metabase для подключения к Trino, стабильно возвращал ошибку аутентификации («Authentication failed: ... X-Trino-User must be sent») независимо от переданного значения параметра `user`. Проблема была решена переходом на драйвер `starburst`, использующий тот же протокол взаимодействия с Trino, но корректно поддерживающий текущую схему заголовков аутентификации; изменений на стороне самого Trino не потребовалось.

## 7. Выводы

Медальонная архитектура на практике реализуется не как последовательность трёх копий одних и тех же данных, а как набор конкретных инженерных решений на каждом слое: слой Bronze хранит источник без изменений и без потери информации; слой Silver — единственное место, где применяются бизнес-фильтры и денормализация (объединение с таблицей `nation` в `dim_customer`, фильтрация по кварталу и признаку возврата в `fct_returned_lineitem`); слой Gold выполняет только группировку и агрегирование, поскольку вся сложность вычислений перенесена на нижележащие слои. Следствием такого распределения ответственности является резкое уменьшение объёма данных от слоя к слою: итоговая витрина Gold занимает около 3 КБ на 20 строк, тогда как основной объём медальона (69 МБ из приблизительно 112 МБ) несёт детализированная таблица `raw_lineitem` слоя Bronze — что соответствует общему принципу: детализированные данные должны храниться на нижних слоях, агрегированные результаты — на верхних.

Эксперимент по сравнению кодеков сжатия показал, что на данных типа `lineitem` (преимущественно числовые и decimal-колонки) разница в степени сжатия между ZSTD и GZIP минимальна (менее одного процента по результатам контролируемого замера), тогда как по скорости записи и чтения ZSTD демонстрирует устойчивое преимущество. Это подтверждает обоснованность выбора ZSTD в качестве кодека по умолчанию для Iceberg-коннектора Trino применительно к данным такого характера; сознательное применение GZIP целесообразно только для действительно холодных, редко читаемых архивных данных, где определяющим фактором является объём занимаемого места, а не скорость доступа.

Полный бенчмарк восьми комбинаций формата и кодека подтвердил, что накладные расходы метаданных каталога Iceberg (манифесты по 8–9 КБ) пренебрежимо малы на фоне десятков и сотен мегабайт данных и не являются практической проблемой на рассмотренных объёмах. Отдельно следует отметить два практических наблюдения, выходящих за рамки табличных данных: во-первых, ограниченный объём доступной памяти привёл к реальному аварийному завершению Trino при нагрузке, близкой к масштабу `sf10`, что подтверждает необходимость подбирать масштаб тестовых данных исходя из доступных ресурсов конкретного стенда, а не только из методических рекомендаций гайда; во-вторых, несовместимость рекомендованного документацией драйвера Metabase с установленной версией Trino показывает, что совместимость инструментов BI-слоя с конкретной версией движка целесообразно проверять эмпирически, не полагаясь исключительно на документацию.
